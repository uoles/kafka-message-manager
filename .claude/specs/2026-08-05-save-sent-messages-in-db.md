# Сохранение отправленных сообщений в базе данных

**Дата:** 2026-08-05  
**Статус:** Спецификация к реализации

## 1. Цель

Сейчас история сообщений, отправленных через веб-интерфейс, хранится только в браузерном `localStorage`. Поэтому история 
зависит от конкретного браузера и origin, не загружается с сервера после перехода на другое устройство, а поведение UI 
не связано с состоянием приложения и авторизованного пользователя.

Необходимо сделать серверное хранение истории отправленных сообщений. После перезапуска Spring Boot-приложения 
авторизованный пользователь должен снова получить свои ранее отправленные сообщения. Записи одного пользователя 
не должны быть доступны другому пользователю.

В рамках задачи требуется:

- создать таблицу `sent_messages` в SQLite через Liquibase;
- создать модель записи и новый репозиторий;
- создать сервисный слой;
- расширить API контроллера отправки и истории;
- подключить историю к веб-интерфейсу;
- добавить модульные тесты для репозитория, сервиса и контроллера.

## 2. Пользовательские сценарии

### 2.1. Отправка сообщения

1. Пользователь проходит аутентификацию и получает JWT.
2. Браузер отправляет `POST /api/kafka/send` с bearer-токеном.
3. Контроллер извлекает `user_id` из `Authentication`/`Jwt subject`; идентификатор не берётся из JSON-запроса.
4. Сервис отправляет сообщение в Kafka.
5. Только после успешной отправки создаётся запись в `sent_messages`.
6. API возвращает результат отправки вместе с идентификатором сохранённой записи и данными, необходимыми для отображения 
и повторной отправки.

Если Kafka не приняла сообщение, запись со статусом успешной отправки не создаётся. Вариант сохранения ошибок как 
отдельных записей допускается только при явном согласовании контракта; в таком случае они должны иметь `status = error` 
и не смешиваться с успешно отправленными сообщениями.

### 2.2. Загрузка истории после перезапуска

1. После открытия страницы браузер отправляет bearer-запрос `GET /api/kafka/sent-messages`.
2. Сервер извлекает пользователя из токена и загружает только его записи.
3. Записи возвращаются в порядке от новых к старым.
4. UI отображает историю после перезапуска приложения, независимо от наличия прежнего состояния в памяти JavaScript.

### 2.3. Очистка истории

Кнопка очистки истории должна удалять серверные записи текущего пользователя через `DELETE /api/kafka/sent-messages`. 
После успешного ответа UI очищает отображаемую историю. Записи других пользователей не затрагиваются.

### 2.4. Повторная отправка

Кнопка `Resend` получает данные выбранной серверной записи и заполняет форму: `topic`, `kafkaAddress`, `messageText` и 
`headers`. Автоматическая отправка без дополнительного действия пользователя не выполняется.

## 3. Критерии готовности

- После перезапуска приложения история отправленных сообщений загружается из SQLite.
- Пользователь A не может получить, удалить или изменить записи пользователя B.
- `user_id` нельзя подменить через тело запроса, query-параметр или path-параметр.
- Успешная отправка Kafka сохраняется один раз.
- Неуспешная отправка не появляется в истории как успешная.
- Порядок выдачи стабилен: `created_at DESC, id DESC`.
- История ограничивается параметром `limit` с безопасным максимальным значением; при необходимости дальнейшего роста 
API можно расширить cursor-пагинацией.
- Существующие операции отправки, health-check и consumer API продолжают работать.
- Liquibase создаёт схему на чистой и существующей базе без ручного SQL.
- Тесты репозитория, сервиса и контроллера проходят.

## 4. Изменения базы данных

### 4.1. Новая таблица

Добавить файл:

`src/main/resources/liquibase/scripts/tables/TABLE.SENT_MESSAGES.sql`

Таблица должна содержать:

| Колонка | Тип SQLite | Ограничения | Назначение |
|---|---|---|---|
| `id` | `TEXT` | `PRIMARY KEY NOT NULL` | UUID записи |
| `user_id` | `TEXT` | `NOT NULL`, FK на `users(id)` | Владелец записи |
| `topic` | `TEXT` | `NOT NULL` | Kafka topic |
| `kafka_address` | `TEXT` | `NOT NULL` | Адрес bootstrap-сервера |
| `message_text` | `TEXT` | `NOT NULL` | Тело отправленного сообщения |
| `headers_json` | `TEXT` | `NOT NULL` | Заголовки в формате JSON |
| `status` | `TEXT` | `NOT NULL` | Например, `success` или `error` |
| `response_message` | `TEXT` | `NOT NULL` | Сообщение результата операции |
| `created_at` | `INTEGER` | `NOT NULL` | Unix epoch milliseconds |

Рекомендуемый внешний ключ:

```sql
FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
```

Добавить индекс:

```sql
CREATE INDEX idx_sended_messages_user_created
    ON sent_messages(user_id, created_at DESC, id DESC);
```

`headers_json` должен хранить пустой объект/массив, а не SQL `NULL`, если заголовки отсутствуют. Формат должен быть 
совместим с `HeaderUtils.serializeHeaders` и `HeaderUtils.deserializeHeaders`.

### 4.2. Подключение миграции

Добавить include в:

`src/main/resources/liquibase/changelog-master.xml`

Так как таблица содержит внешний ключ на `users`, миграция должна выполняться после создания таблицы пользователей. 
Порядок include необходимо проверить относительно `TABLE.USERS.sql`. Создание таблицы в Java, `SQLiteDatabaseConfig` 
или репозитории запрещено.

При использовании SQLite необходимо проверить, что Liquibase-соединение применяет `PRAGMA foreign_keys = ON`. 
Если проектная конфигурация уже включает этот режим, повторять конфигурацию не нужно.

## 5. Модель и DTO

Добавить immutable-модель записи в `ru.uoles.kafka.sender.model`, предпочтительно Java record, например `SendedMessage`:

- `UUID id`;
- `UUID userId`;
- `String topic`;
- `String kafkaAddress`;
- `String messageText`;
- `Map<String, String> headers` или существующий тип заголовков;
- `String status`;
- `String responseMessage`;
- `Instant createdAt`.

Внешний DTO ответа не должен раскрывать внутренние поля, если они не нужны UI. `userId` не следует возвращать браузеру: 
владелец уже определяется текущим JWT.

Ответ истории должен содержать `id`, `topic`, `kafkaAddress`, `messageText`, `headers`, `status`, `responseMessage` и 
`createdAt`. Поля можно оформить отдельным `SendedMessageResponse`, чтобы не связывать API с persistence-моделью.

Ответ `POST /api/kafka/send` следует расширить идентификатором созданной записи и данными отправки, сохранив 
существующие поля `status`, `message`, `topic`, `kafkaAddress`, `timestamp` для обратной совместимости.

## 6. Репозиторий

Добавить:

`src/main/java/ru/uoles/kafka/sender/kafka/repository/SendedMessagesRepository.java`

Репозиторий должен использовать `JdbcTemplate`, `@Repository` и constructor injection в стиле `ReceivedMessagesRepository`.

Минимальный API репозитория:

```java
UUID save(SendedMessage message);
List<SendedMessage> findByUserId(UUID userId, int limit);
int deleteByUserId(UUID userId);
Optional<SendedMessage> findByIdAndUserId(UUID id, UUID userId);
```

Требования к SQL:

- все значения передаются параметрами, без конкатенации пользовательского ввода;
- UUID сохраняются как `UUID.toString()` и восстанавливаются через `UUID.fromString()`;
- `Instant` сохраняется как `toEpochMilli()`;
- история фильтруется обязательным `user_id`;
- выборка сортируется `created_at DESC, id DESC`;
- `limit` проверяется до передачи в SQL и ограничивается константой сервиса/контроллера;
- headers сериализуются и десериализуются через существующий `HeaderUtils`;
- `deleteByUserId` удаляет только записи текущего владельца.

Если `save` получает запись без `id`, UUID должен быть сгенерирован сервисом до вызова репозитория. `user_id` 
должен быть обязательным и не может быть `null`.

## 7. Сервис

Добавить интерфейс и реализацию в:

- `src/main/java/ru/uoles/kafka/sender/kafka/service/SendedMessagesService.java`;
- `src/main/java/ru/uoles/kafka/sender/kafka/service/SendedMessagesServiceImpl.java`.

Сервис отвечает за:

- создание записи после подтверждённой отправки Kafka;
- загрузку истории по `userId`;
- очистку истории по `userId`;
- проверку безопасного лимита выдачи;
- преобразование persistence-модели в DTO.

Сервис не должен принимать `userId` из `MessageRequest`. Для операций HTTP контроллер передаёт идентификатор, 
полученный из JWT. Для обычного пользователя доступ всегда owner-scoped. Роли `MODERATOR` и `ADMIN` не получают 
глобальный доступ автоматически: если понадобится административный просмотр, его следует оформить отдельным endpoint 
и отдельной авторизационной политикой.

Сохранение и отправка должны иметь определённую семантику отказа. Рекомендуемый вариант:

1. Kafka send завершился успешно.
2. Выполняется запись в SQLite.
3. Если запись не сохранилась, API возвращает внутреннюю ошибку и логирует техническую причину без 
JWT/паролей/authorization header; в документации нужно явно указать, что Kafka уже могла принять сообщение.

## 8. Изменения контроллера

Изменить:

`src/main/java/ru/uoles/kafka/sender/controller/MessageController.java`

### 8.1. Отправка

Изменить сигнатуру `sendMessage`, добавив `Authentication authentication`. Идентификатор получать тем же способом, 
который уже используется для consumer ownership: из subject JWT через существующую вспомогательную логику 
`userId(authentication)`.

После успешного вызова `KafkaMessageService.sendMessage(...)` вызвать `SendedMessagesService`. При исключении Kafka 
не вызывать сохранение успешной записи.

Не логировать текст сообщения, содержимое authorization header, JWT, пароль или hash пароля. Существующее логирование
topic/address проверить на соответствие проектной политике и не расширять чувствительными данными.

### 8.2. Загрузка

Добавить защищённый endpoint:

```http
GET /api/kafka/sent-messages?limit=100
Authorization: Bearer <jwt>
```

Ожидаемый ответ — массив DTO или объект с `messages` и метаданными лимита. В первом варианте достаточно массива, 
если pagination не вводится сейчас. Для невалидного/отсутствующего JWT применяется существующая security-конфигурация.

### 8.3. Очистка

Добавить защищённый endpoint:

```http
DELETE /api/kafka/sent-messages
Authorization: Bearer <jwt>
```

Ответ должен содержать число удалённых записей либо стандартный успешный статус `204 No Content`. Операция должна 
быть идемпотентной для пустой истории.

## 9. Изменения веб-интерфейса

Изменить актуальные классические скрипты, загружаемые `index.html` в порядке зависимостей. Не нарушать загрузку 
Bootstrap до скрипта, использующего Bootstrap API.

Требования:

- при инициализации вызвать `GET /api/kafka/sent-messages` через общий auth-wrapper;
- добавить `Authorization: Bearer <token>` автоматически средствами существующего auth state;
- прекратить считать `localStorage` единственным источником истины;
- после успешного POST добавлять в UI запись из ответа сервера, включая `id`;
- `Resend` заполняет форму серверными полями и не отправляет сообщение автоматически;
- `Clear history` вызывает DELETE и очищает UI только после успешного ответа;
- обработать `401/403`: очистить сессию согласно существующему auth flow и направить пользователя на login;
- не показывать чужие записи даже при подмене локального состояния.

Нужно выбрать и зафиксировать стратегию перехода с текущего `localStorage`:

1. предпочтительно удалить старые локальные записи после первой успешной загрузки серверной истории; либо
2. выполнить одноразовую миграцию только тех записей, которые нельзя подтвердить сервером, отдельным endpoint с 
валидацией; либо
3. оставить localStorage только как временный offline-cache, но всегда обновлять его из owner-scoped серверного ответа.

Не отправлять старые локальные записи на сервер без отдельного API и явного решения о доверии к этим данным.

## 11. Ограничения и решения по совместимости

- Не использовать `received_messages` для истории отправок: это журнал сообщений, полученных динамическими consumer-ами,
с другой моделью владения и жизненным циклом.
- Не создавать таблицу через `CREATE TABLE` при старте Java-кода; схема принадлежит Liquibase.
- Не принимать `user_id` в `MessageRequest`, DTO истории для создания или query-параметрах.
- Не менять request-scoped адрес Kafka на глобальный `spring.kafka` без отдельного изменения API-контракта.
- Существующие nullable owner rows в таблице `consumers` не являются основанием делать `sent_messages.user_id` nullable.
- Для больших историй в следующей итерации добавить cursor pagination (`before`, `limit`) вместо неограниченного `SELECT`.
- Документировать в README новые endpoint-ы и то, что браузерная история теперь является серверной и привязана к пользователю.
